## What sigillum is

`gitlab.com/phpboyscout/sigillum` is a standalone signing and encrypted-report
CLI for the phpboyscout ecosystem, built on
[go-tool-base](https://gitlab.com/phpboyscout/go-tool-base). It produces
signatures over release artefacts, OpenPGP for checksum manifests and minisign
for the artefacts themselves, and exposes the ecosystem's `sign` and `keys`
commands as top-level commands.

**Why it exists, beyond the README.** The same signing surface is already
reachable as `gtb sign` / `gtb keys`, so sigillum is not new capability. It
exists so a project whose release pipeline is not Go, and has no reason to build
a gtb-based tool, can still install one small binary and sign. That framing
settles scope questions: if a change only helps gtb-based tools, it almost
certainly belongs upstream in `go/signing-cli`, not here.

**What it deliberately does not do** is the sharpest way to see its edges, and it
is written down: see
[`docs/explanation/what-sigillum-does-not-do.md`](docs/explanation/what-sigillum-does-not-do.md).
The headline is that **there is no `verify` command.** sigillum signs and
decrypts; it does not verify. Verification belongs where the trust anchor lives
(the consumer already knows which key it trusts), so it is done with
`gpg --verify`, `minisign -Vm`, or the `go/signing/verify` library, never a
subcommand here. See the trap below about the binary's own description string.

## Status

Pre-1.0. The `sign` / `keys` / `certificate` / `decrypt` surface is in place and
exercised end to end by the behaviour suite (`features/signing.feature`,
`features/decrypt.feature`). Named signing backend instances
(`--backend aws-kms:prod?kms-region=eu-west-1`, from `go/signing-cli` spec 0001)
are live. Production signing runs through AWS KMS over OIDC.

Do not hardcode a version anywhere. `git tag` (or the releases page) is the
source of truth for where the version actually is; a local checkout's tags can
lag the remote, so a bare `git describe` may read older than the cut release.

## It sits on the signing and encryption families

Its direct toolkit dependencies say what it actually consumes:

- **`go/signing`, `go/signing-cli`, `go/signing-aws-kms`.** The real signing
  logic lives in `go/signing`; `go/signing-cli` owns the shareable command
  surface, and this tool exposes that surface top level rather than reimplementing
  it. A change to a shape `go/signing` owns reaches here.
- **`go/encryption`, `go/encryption-aws-kms`** for the encrypted-report half.
- **`go/credentials`, `go/errorhandling`, `go/errors`** as the common spine.

Everything else in `go.mod` arrives through go-tool-base and is marked indirect.

**Backends are compiled in by blank import.** `cmd/sigillum/signing.go`
registers the signing backends (aws-kms + local), `cmd/sigillum/encryption.go`
the key services `decrypt` and `certificate` resolve against (aws-kms + local
PEM), and `cmd/sigillum/keychain.go` (gtb-generated) the OS keychain. Adding a
backend is a blank import here; a regulated build drops one and linker dead-code
elimination keeps the unused SDK out. Nothing else references these packages.

## It is a gtb project

`.gtb/manifest.yaml` describes the application and `.gtb/ignore` marks what the
generator must not overwrite. Use the project-pinned gtb rather than the one on
your PATH; the manifest pins `v0.37.1`. Do not hand-edit
`// Code generated by gtb` files; re-run the generator or add non-generated
files alongside. See **work-on-a-gtb-project**.

## The quality gate

`just ci` runs `tidy`, `generate`, `test`, `test-race` and `lint`. There is a
`features/` directory, so the suite includes Godog scenarios as well as unit
tests. **The e2e and integration suites are env-gated and silently pass without
the variable** (a bare `go test ./test/e2e/...` runs nothing and reports `ok`):
use `just test-e2e` (`INT_TEST_E2E=1`) and `just test-integration`
(`INT_TEST=1`).

## Traps

The parts that have bitten someone, or that look wrong and are not. This tool
handles keys and signatures, so the keys-and-signing traps matter more than most.

- **The binary's own description says "signing and verification CLI"
  (`pkg/cmd/root/cmd.go`), and there is no verify command.** This is a known,
  deliberate asymmetry, not a missing feature. Do not "fix" it by adding a
  `verify` subcommand; verification is out of scope on purpose. If anything, the
  description string is the half that overreaches.
- **One key cannot serve both signature formats.** `openpgp` needs an RSA key;
  `minisign` needs an Ed25519 key. `keys mint` inherits the RSA-only constraint
  (it builds an OpenPGP entity). The cause is upstream and structural: go-crypto's
  OpenPGP Ed25519 branch requires a concrete `*ed25519.PrivateKey` and offers no
  `crypto.Signer` fall-through, so an opaque KMS-held Ed25519 key cannot drive it
  at all. A project publishing both a signed manifest and signed artefacts needs
  two keys; the error messages name the mismatch.
- **The private half of a signing or decryption key never leaves the key
  service.** Signing and decrypting are KMS/key-service calls, not operations on
  a key on disk; that premise is what the `decrypt` and KMS `sign` paths are
  built on. Do not add a code path that pulls a private key out to sign or
  decrypt locally.
- **Named backend instances are a selector string, not new flags.** `--backend`
  takes `type[:instance][?k=v&k=v]`: a bare `<type>` resolves the registered
  default (unchanged), and `<type>:<instance>` mints a fresh instance configured
  by the query. `type:instance` only works if the backend module registered a
  factory; a registered-default-without-a-factory gives a clear error saying so.
- **A partial bump of the signing family can advertise a flag with no capability
  behind it.** Go's minimum-version selection means bumping only `signing-cli`
  while its `go/signing` floor predates a capability leaves the CLI offering a
  flag the linked registry cannot honour (this shipped once as the
  "flag-without-capability" footgun and was fixed by raising the floor). When
  re-pinning, move `go/signing`, `go/signing-cli` and the backends together and
  check the resolved versions with `go list -m`, not just the `go.mod` require
  lines.
- **releaser-pleaser majors a pre-1.0 break to v1.0.0.** A `feat!:` or a
  breaking-change footer cuts `v1.0.0` even from `v0.x` (this genuinely
  mis-released a sibling). Read **pre-1-0-release-safety** before writing any
  commit or MR description that could carry a break, and do not write the literal
  breaking-change token in prose; neutralise it in backticks if you must mention
  it.
- **Do not reintroduce `golang.org/x/crypto/openpgp`.** It is unmaintained and
  carries advisory GO-2026-5932 with no fix; the OpenPGP path uses ProtonMail's
  `go-crypto` fork. Check `go list -deps` if `govulncheck` flags it.

## House rules

- Linear history. Rebase and fast-forward; never squash-merge from the UI.
- Conventional Commits, and the type decides whether a release is cut. Only
  `feat` and `fix` release; a change that repoints or removes a public interface
  is `feat`, not `refactor`, or it lands and never ships.
- No AI attribution in anything published, and never at-mention anyone.
- Never cut a release yourself. That is the maintainer's call, every time.
- Specs live on the
  [project wiki](https://gitlab.com/phpboyscout/sigillum/-/wikis/specs/home), not
  in this repo; `docs/development/specs/index.md` is a register that links out.
  Do not commit without explicit approval: present a summary and a proposed
  message, then wait.
